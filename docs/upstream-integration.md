# 上游迁移与行为对齐手册

本文用于处理“上游已经通过，本 fork 却失败”“迁移后的物理编码与上游不同”以及“测试通过但候选行为已经漂移”等问题。目标不是逐行复制上游，而是在本仓库布局、辅序和功能合同下复现同一语义，并留下可定位回归的证据。

## 基本原则

- 上游提交、子模块提交、Mira/librime 版本、方案配置和用户词频状态共同决定候选行为；它们都是实验输入，不能把工具升级当作无关环境变化。
- 先确认上游当前实际行为，再解释代码。README、旧测试和提交说明只能提供线索，不能代替在干净部署中的候选结果。
- 一次只改变一个变量。尚未确认是配置权重、运行时版本还是测试口径的问题时，不改分段、顶功、处理器顺序或 Lua 路由。
- 迁移编码时先还原语义，再映射物理键。不能因上游示例末尾是 `v`，就在本地也追加 `v`。
- 上游测试只提供场景意图和目标字词句，不提供可直接复制的本地输入串、码长、候选位次或断言。本仓库的测试必须由本地方案合同重新推导。
- “测试绿”不等于“行为对齐”。宽松的候选存在性断言可能掩盖首选漂移，完整测试也可能被单个状态写入或缓存污染。

## 标准诊断流程

### 1. 固定证据和预期合同

开始修改前记录以下信息：

- 上游仓库提交、相关子模块提交和 tag；
- fork 的基线提交；
- Mira/librime 的确切版本或下载产物哈希；
- 输入串、逐键或整串输入方式、预编辑串、第一页候选顺序和上屏结果；
- 用户词典、编译缓存和部署是否为空；
- 预期是“某项首选”“某项在首页／全部候选中存在”，还是仅要求方案可部署。

工具的 `latest` 下载地址是可变输入。正式 CI 可以跟随上游 latest；故障复盘必须另外记录当时实际得到的版本或哈希，才能复现新旧差异。

### 2. 先建立受控对照矩阵

至少比较下列三个维度，不要只跑 fork 的完整测试：

| 维度 | 对照项 |
| --- | --- |
| 源码 | 上游原样 checkout／fork 基线 |
| 运行时 | 历史固定 Mira／上游当前 Mira |
| 待验证配置 | 上游值／fork 值 |

每一格先缩成单方案、单 deploy、单用例、单轮，并使用干净用户词典与独立缓存。记录实际候选，不只记录进程退出码。矩阵通常能直接区分四类原因：上游本身回归、运行时行为变化、fork 配置漂移、fork 专属处理链干扰。

本仓库 GitHub Actions 的“测试”工作流支持 `workflow_dispatch` 参数 `schema` 和 `deploy`。先用它只跑目标 schema/deploy；最小用例稳定后再依次扩大到该方案全部 deploy、九方案全量测试。不要用 WSL 或 Docker 中的 Mira 代替仓库要求的真实候选环境。

常规 CI 对每个发布方案同时运行 `mira-rime1.13.1` 和 `mira-rime1.17`：前者对应当前稳定版小狼毫 0.17.4 的内核，后者对应当前稳定 librime。排查版本差异时仍应记录 Mira 资产更新时间与输出的 SHA-256；双版本都通过才表示发布包同时兼容这两类用户，不能用其中一边的结果代替另一边。

### 3. 在正确层级修复

按以下顺序排查，前一层已排除后再进入后一层：

1. 测试是否准确表达上游合同；
2. 工具版本、依赖、缓存和用户词频状态是否一致；
3. schema 的翻译器权重、tag、前缀和组件顺序是否一致；
4. 本地布局是否需要语义重映射；
5. 最后才检查 Lua 分段、重投、顶功和候选过滤。

如果只改一个 schema 权重就能在最新运行时复现上游，不应同时改反引号分段、popping 或 Lua 路由。诊断性提交如果后来证明方向错误，应在合入前剔除，不把试错路径留成新的行为依赖。

### 4. 写能够发现行为漂移的回归

- 迁移上游新增测试时，可以沿用其目标字、词、句和功能场景；输入编码、追加辅码、选重键、候选位次、码长与上屏方式必须在本地方案中重新求得。
- 要求首选时断言 `cand[1].text`，不要仅用 `has()` 或 `page()`。
- 上游只承诺首选时，不额外要求旧候选继续存在；若确有“首选＋保留候选”两项合同，拆成两条断言。
- 会写用户词典或改变动态码长的测试使用独立 deploy；依赖原始词频的用例排在任何上屏类用例之前。
- 对候选排序敏感的回归保存具体输入和目标字词，不只断言候选数量。
- 语义迁移同时覆盖生成器、生成产物、schema、文档和测试，避免测试示例仍沿用旧物理键。

迁移一条上游测试时按以下顺序处理：

1. 用自然语言写清它要保护的功能和目标字词句；
2. 确认该功能在本地对应哪个方案、翻译器和动态状态；
3. 从本地 schema、辅序、生成器或运行时空桶重新推导输入；
4. 在干净的本地方案部署中观察候选和上屏行为；
5. 按本地合同写断言，再把结果与上游的功能意图对照。

只有共享合同本身要求一致时，才要求两边的候选结果一致；布局、辅序、固定词表或空桶不同导致的本地差异，应验证其本地语义正确性，而不是强行复刻上游物理表现。

## 布局相关迁移必须走语义链

多字词追加辅码至少经过以下推导，缺一不可：

1. 根据词长选择二／三／四字词辅序；
2. 根据辅序确定取词中第几个字；
3. 确定该字所取的属性，例如字形首笔或声调；
4. 用本地 `shapeKeysByMeaning` 或 `toneKeysByTone` 把属性映射到物理键；
5. 在本地方案中验证候选字词和排序。

例如冰雪弎拼四字词使用辅序 `23`，`垃圾回收` 的第一辅取第 2 字“圾”；“圾”为一声，而本地一声键是 `i`，所以回归输入是 `ljhei`。上游旧示例的 `ljhev` 只反映上游当时的物理映射，不能直接迁入。

经典方案迁移同样遵守此规则。冰雪键道、冰雪三拼只冻结经典声韵布局，不冻结旧功能缺陷；AA/AAB 空桶、630、字母、数字、生僻字、大写补韵和当前 Lua 修复都应按经典音码重新计算，而不是复制冰雪健道或冰雪弎拼的码表。

## Benchmark 的行为合同

单字最长合同 `AUBBBB` 表示“最多追加四辅”，不是强制输入六码。`A`、`AU`、`AUB`、`AUBB`、`AUBBB` 和 `AUBBBB` 都可能是合法路径；二、三、四字词也同时有标准码和扩展码。

Benchmark 必须查询实际候选状态，并在动态首选后置、用户学习和选重规则下寻找最短可上屏路径。优化时先比较选重次数，再比较实际按键数和标准码长度；目标已经首选时，不为省一个 Space 继续补无必要的辅助码。不能拿固定六码的最终候选名次代替真实输入过程，也不能假设某个候选会在全程固定为第 1 或第 2。

## 本次清韵案例留下的结论

提交 `293653d` 只把冰雪清韵的 `radical/initial_quality` 从 `2` 降到 `1`，没有批量修改“琰”或其他单字词频。该修改是历史固定 Mira 下为通过候选测试留下的兼容性措施。

到 2026-11-05，上游原样方案配合当前 Mira 使用 `initial_quality: 2` 可以通过；fork 恢复为 `2` 后也能通过九方案全量测试。相反，当前 Mira 配合 `initial_quality: 1` 时，输入 `` `wangyan `` 的首选会变为“网眼”，不再与上游首选“琰”对齐。旧用例只检查“琰”是否出现在候选中，因此可能继续通过，却没有守住首选合同。

正确修复是恢复上游权重 `2`，为该输入增加隔离 deploy 和 `cand[1].text == "琰"` 的精确回归，并保留其他现有功能；不需要修改反引号分段、顶功重投或 Lua 路由。这个案例说明：先做“上游／fork × 旧／新 Mira × 配置 1／2”的最小矩阵，远比围绕完整处理链反复试改更快。
