# 周期冷存与版本管理

冷存只使用地址映射和说明，不从工作目录建立指向冷盘的目录联接或符号链接。冷盘批次完成后冻结，查阅时显式指定冷盘路径，重新运行时恢复副本。源盘副本已删除的迁移属于空间整理，不是两份独立备份。

## Git 与冷盘的分工

| 保存位置 | 内容 | 更新方式 |
| --- | --- | --- |
| Git：本规范、两批说明、`docs/cold-storage/catalog.json` | 批次身份、原地址与冷地址、已知代码分支及完整提交、文件数与字节数、详细清单 SHA-256 | 每次冷存独立提交；推送两个 fork 并核对远端提交。 |
| 冷盘：`N:\snow_pinyin\rime-snow-pinyin\<batch>/` | 实际数据、逐文件清单、历史依据、操作日志、恢复说明 | 批次完成后冻结，不覆盖旧数据，不直接在其中运行实验。 |
| 两边批次清单目录 | `index.json`、`*.files.jsonl`、说明与回执 | 两边副本校验相同；Git 总索引保存其摘要，详细内容不全部塞入源码仓库。 |

Git 的分支名只是方便理解的标签，完整 commit 才是代码锚点。必须区分生成数据的 source commit、实验工作树 HEAD、执行归档的 archive HEAD 和记录归档的 documentation commit。没有记录的来源标为未知，不能将归档时的 main HEAD 当作全部文件来源。代码或数据含未提交改动时，保存 diff、未跟踪文件、子模块提交和实际冻结源码的哈希；单独一个 commit 不足以恢复它们。

不能仅靠记录 SHA 保住尚未合入的历史对象：移除检出或计划删除分支前，确认相关 commit 仍由长期引用保留；有独有或私有对象时，另外生成 Git bundle 并执行 bundle verify，子模块各自处理。已有两批工作树归档保存了专属 Git 管理数据快照，其私有对象恢复需单独检查，不声称已形成可移植的 bundle。不要借用发布 tag 标记本机冷存，也不为归档独立递增发布版本。

## 批次与清单合同

新批次 ID 使用 UTC 时间戳、归档 HEAD 短 SHA 和随机尾缀，避免同日多批碰撞；分支名作为字段保存，不能直接拼进路径。旧两批保留现有 ID。每批记录 `schemaVersion`、`batchId`、UTC 创建/封存时间、仓库身份、来源/归档提交、脏状态、子模块、工具版本、原地址、冷盘相对地址、文件数、字节数及文件清单摘要。

逐文件记录相对路径、长度、SHA-256；目录链接单列类型和目标，不跟随链接递归复制。历史快照原有的外部依赖链接只作为证据保存，不视为可运行依赖；跨机器恢复时显式安装依赖。新归档不建立连接冷热位置的链接，确需依赖时用清单表达关系。旧两批创建的 64 个别名已移除；冷盘缓存和数据原件完整保留。

当前总索引以 `coldRoot + coldRelative` 定位，`original` 仅表示历史来源地址；同名路径以后可以生成新数据，不能据此把新旧两代混为一份。`manifestSha256` 绑定对应的逐文件清单，`indexSha256` 绑定当前批次索引。后续访问或位置调整通过新回执记录，并在 Git 提交更新后的索引摘要；旧来源信息和旧回执保留。封存 payload 不随文档修订改写。

## 每次执行顺序

1. 明确选择本批次路径，检查冷盘身份、容量、目标未占用及相关写入者；记录 plan 和来源状态。停止仍在写的实验，活数据库按其一致性合同生成快照，不把源根目录里的链接当普通文件遍历。
2. 复制到新批次的暂存位置并记录操作日志；复制完核对计划的完整集合、每个文件的长度和 SHA-256，以及源是否仍与冻结清单一致。出现失败时保存两边，尚未发布完整批次前不删除源。
3. 全批次验证成功后封存，生成完整清单及恢复说明，再按计划逐项复查源未变化后删除原副本。记录已删、未删、失败状态；中断后按回执检查继续，不能只凭目录存在跳过校验。
4. 两边写相同地址映射、清单与回执，不创建旧路径入口。更新 Git 总索引和冷盘总目录，核对清单摘要。仅在全部必需步骤完成后写 completed 状态；部分失败明确保留为未完成。
5. 提交规范/总索引/本批摘要并推送；操作提交号可写入单独 completion receipt，避免为回填自己的 commit 反复修改同一索引。以后定期按清单做完整哈希复核，明确区分历史迁移时验证通过与最近一次检查通过。

归档和源删除分开记录，不因冷盘目录已存在就视为成功，不重复执行一次性删除脚本。现有 `transfer.py`、`transfer.ps1` 等只是历史批次证据，不能用来创建后续批次或重新建立链接。后续若实现通用工具，至少提供 plan、copy、verify、finalize、restore 和只读 status，具备防重叠、断点恢复及链接隔离检查。

## 查找与恢复

先查 Git 总索引的 original 或批次 ID，再用 coldRelative 查到目标；核验详细清单摘要后读取文件。冷盘离线时标记不可用，不自动回退到同名新目录。恢复到独立且尚不存在的工作目录，核验后再运行，原冷盘批次继续保留。需要旧绝对路径的脚本在恢复副本或配置中调整；恢复操作单独记录目标、时间、基准批次和验证结果。

目前应优先完成的后续工作是：审阅两个有未提交改动的工作树，决定哪些变更应提交或另行冻结；查明 `fix/qingyun-reverse` 未合入提交是否仍有用途；为后续归档建立通用工具及定期只读核验，而不是继续无差别删除剩余缓存。以上工作树的内容处理需要单独审阅，本规范不授权丢弃其变更。
