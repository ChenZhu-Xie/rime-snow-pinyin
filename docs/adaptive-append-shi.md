# 单音节「×是」自适应上屏

`]` 先按当前选中候选分流：多字候选直接取末字；单字候选且输入为完整或不完整的单音节编码时，查找所有兼容读音的「×是」二字词，不把首字锁定为当前单字。无匹配时沿用选中单字追加「是」。已有确认片段、光标回补、反查及独立形辅输入不进入此查询。

## 直接词典查询

系统词从生产的 base、ext、tencent、user 四份词库逐行提取，只保存末字为「是」、读音为两个音节且末音为 `shi4` 的二字词。`scripts/generate-append-shi.ts` 生成 `lua/snow/append_shi_words.txt`（首字读音、词、系统权重；相同词与读音取最大权重），同时生成十一方案的单音节前缀到读音及标准词码映射。`--check` 同时校验两类产物；词库变化后须重新生成。仅加载小型索引，不展开完整词库。系统词典的 Lua `lookup_words` 接口不能直接查询任意多音节规范码，因此使用生成索引。

用户词通过当前方案的 `Memory.user_dict:lookup_words(首音 .. " shi4", false, 0)` 实时读取。系统索引中没有的新用户词也能参与，不缓存最终答案；同一次按键内重复读音只查一次。标准词码只用于读取匹配的置顶项，不送入引擎，不重建菜单，也不查询三、四字词。

排序只比较「×是」：匹配的置顶词优先（多个匹配置顶按位置数值优先）；其余词中未后置的优先，再按是否存在用户学习记录、用户权重或系统权重降序比较。同优先级以文本稳定排序。普通候选的置顶不影响此集合。手动置顶的新词须验证首字读音，避免跨音节误入。多读音或重复路线取最优记录。后置状态由普通后置过滤器发布到当前 context 的 `snow_postpone_known` 属性，快捷查询只读；这里只比较「×是」之间的后置关系，不复现完整菜单的前十项插槽及词长混排位置。

直接上屏调用 `snow.commit_text` 后清空输入，不调用 `context.select`、`context.commit` 或任何用户词典写入接口，不改变标准词码或简拼的学习排名。繁体开关开启时使用 `s2t.json` 转换输出。输入统计和文字收集仍收到直接上屏通知。

本地验证包括 `spec/append_shi.test.lua`（禁止输入重写、菜单读取和原生提交；覆盖新用户词、匹配置顶、后置、负数及零权重、去重和无匹配）、以词定字及后置测试，以及生成校验。实际候选和延迟仅在 GitHub Actions 验证鹮道。以下历史诊断描述旧的完整菜单架构，不是新架构的性能结果。

## 性能诊断（2026-11-27）

新直接词典架构 `b4a2093` 的鹮道定向正式测试（运行 `46023277460`，200 轮，无诊断）通过：`]` 首次 24.51 ms，重复 199 次 P50 1.46 ms、P95 1.65 ms、P99 1.87 ms、最大 1.98 ms；重复阶段没有超过 16 ms 的 `]`。整个 `b]` 场景包含 `b` 和 `]`，重复事件 P99 为 7.21 ms，不能混称为 `]` 的 P99。本次仅验证鹮道该场景，不代表十一方案完整性能门禁；以下为旧架构诊断。

鹮道 `b]` 的只读上屏基准仍未通过 50 ms 门槛。`d5fc764` 的正式重复输入 P99 为 60.41 ms，`8b5f8bc` 为 70.51 ms；不同运行有环境波动，不能据此宣称后一轮改动提速。`d656743` 的鹮道定向功能验证通过。

`40a47a2` 的分路线诊断显示：五条标准词码的菜单生成各约 7–14 ms，首个匹配词只需扫描 1–2 个候选，扫描约 0.01–0.03 ms；优先级预查约 0.12–0.15 ms。主要开销发生在标准菜单生成，而非末字匹配。诊断采用 CPU 时间，与端到端墙钟延迟不同；开启诊断的运行不作为正式性能门禁结果。

空用户库跳过学习排序整批预取的实验 `8356d79`，正式重复输入 P99 为 72.67 ms，没有可确认的收益，已撤回该快速路径。尚不能宣布性能问题解决；继续优化应测量标准翻译器及各过滤器内部开销，保留学习、置顶、后置和词长平衡语义。

`a2985f4` 的细分诊断进一步排除了「学习过滤器预取太多」作为主要解释：学习过滤器拉取上游候选约 0.01–0.10 ms，词长平衡拉取上游约 0.9–2.1 ms，实际每条菜单只有 5–35 项，没有达到 120 项。这里的拉取计时不含上游惰性协程创建时已经执行的首次取词，也不等于过滤器总耗时，不能把这些数值直接相加当作完整分解。

神韵原生二字词路径首次查询约 0.10–0.14 ms，三字词路径约 2.0–4.2 ms，四字词路径约 2.9–6.1 ms。同一四码兼容三、四字词，因此完整标准菜单会启动这些路径；词长平衡和首选后置可能受其影响，不能在没有等价性证明时直接删掉。五条路线的完整菜单生成约 9–19 ms，尚有首次查询之外的引擎开销未分解。此次为带诊断的 CPU 时间观测，不据此判断运行之间的性能回退，也不能认定 librime 已到不可优化的下限。
