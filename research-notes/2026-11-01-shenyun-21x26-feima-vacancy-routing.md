# 神韵 21×26 飞码四码顶空桶路由讨论

> 状态：本次讨论的研究记录。现行两套 21×26 神韵方案行为无需因此调整；容量、文档和代表性候选回归已经补充，文中的 `AB`、`AUB` 保留域尚未纳入产品设计，也不构成发布计划。
>
> 日期：2026-11-01。

## 讨论目标

冰雪神韵·形和冰雪神韵·调采用飞花式飞码四码顶结构。需要确认四码集合中二、三、四字词如何依据合法音节和 `A/B` 键类判长，以及第一音节位置的空 `AB`、`AUB` 是否需要立即利用。

本文使用以下记号：

- `A`：21 个声键，当前为 `bpmfdtnlgkhjqwvxrzcsy`；
- `B`：5 个辅键，当前为 `aeuio`；
- `U`：26 个小写字母，并且 `U = A ∪ B`、`A ∩ B = ∅`；
- “合法 `AU`”：按当前空桶口径能在系统单字词典中形成完整单字音节的二键码；
- “空桶”或“不合法 `AU`”：不能形成上述完整单字音节的二键码。

现行标准编码为：

```text
单字：A / AU / AUB / AUBB
二字：A₁U₁A₂U₂[B₂B₁]
三字：A₁A₂A₃ / A₁A₂A₃U₃[B₁B₂]
四字：A₁A₂A₃A₄[B₁B₂]
```

从纯键类看，四码空间 `AUAU` 同时覆盖二字词 `AUAU`、三字词 `AAAU` 和四字词 `AAAA`。它是多个标准编码族的键形并集，具体词长不能只看四个按键的表面形状，仍须结合第 1～2 码和第 3～4 码能否形成合法音节。

## 四码判长结论

第 3～4 码构成 `A₃U₃` 时，应按第 4 键所属集合和音节合法性分流：

| 第 3～4 码 | 解释 |
| --- | --- |
| 合法 `AU` | 可以走三字词 `AAAU`；若第 1～2 码也形成合法 `AU`，同码还可以保留二字词 `AUAU` 候选 |
| 空 `AA` | 第 4 键仍属于声键，可以作为第四字声码，只走四字词 `AAAA` 路线 |
| 空 `AB` | 第 4 键不可能是第四字声码，改作三字词第一辅码，走 `AAA+B` 路线 |

因此，“第 3～4 码为空桶”本身不足以推断三字词。只有空 `AB` 才能排除四字词并推断 `AAA+B`；空 `AA` 仍须保留四字词路线。

第 1～2 码构成 `A₁U₁` 时，同样需要区分 `AA` 与 `AB`：

| 第 1～2 码 | 解释 |
| --- | --- |
| 合法 `AU` | 保留单字 `AU[B...]` 和二字词 `AUAU[B...]` 路线 |
| 空 `AA` | 两键都可以解释为声码，进入声声二字词短码 `AA[B...]` |
| 空 `AB` | 第 2 键不是声键，不能解释成二字词 `AA`，也没有合法单字；目前作为自然无候选的保留域 |

因此，“第 1～2 码为空桶”也不足以推断二字词。只有空 `AA` 才进入声声二字词；空 `AB` 应与二字词路线分开。

## 当前 21×26 空间测算

按 Overall-17 映射和 Common399 结构音节集合统计：

| 项目 | 数量 |
| --- | ---: |
| `A×U` 总容量 | 546 |
| Common399 占用 | 399 |
| 结构空桶 | 147 |
| 其中空 `AA` | 138 |
| 其中空 `AB` | 9 |

按当前系统单字词典及 `vacancy.lua` 的运行时口径统计：

| 项目 | 数量 |
| --- | ---: |
| 运行时空桶 | 143 |
| 其中空 `AA` | 134 |
| 其中空 `AB` | 9 |

当前 9 个空 `AB` 为：

```text
be pe gi ki hi je qe ra yu
```

结构空桶与运行时空桶不能混为一谈。前者来自冻结音节集合与映射，适合用来设计需要长期稳定的功能码；后者随系统词典、扩展音节和映射变化，用于当前候选路由。当前两种口径恰好具有相同的 9 个空 `AB`，不代表未来会自动保持不变。

## `AB/AUB/AUBB` 保留域容量

9 个空 `AB` 可以形成一棵很小但干净的保留子树：

| 层级 | 容量 | 说明 |
| --- | ---: | --- |
| `AB` | 9 | 二码入口 |
| `AUB`，此处 `AU` 特指上述空 `AB` | `9×5=45` | 再接一个辅键 |
| `AUBB` | `9×25=225` | 再接两个辅键 |
| 合计 | 279 | 包含二、三、四码三个层级 |

若只仿照“二码入口＋一个五选一后缀”的分层使用，则是 `9×(1+5)=54` 个槽，可以非正式地称为“小 54”，不应称为“630”。传统 630 的容量结构是 `21×(5+25)=630`，两者不是同一个规模。

本次讨论没有为这 54 或 279 个槽指定实际用途。可选方向包括特殊功能入口、命令、未来扩展或继续留空，但在需求和交互协议明确前不应填入普通词语。

## 现实现核对

当前 [`lua/snow/shenyun.lua`](../lua/snow/shenyun.lua) 的实际路由已经满足核心判长要求：

- 第一对只有在两个键都属于 `A` 且为空桶时才启用 `AA` 二字词路线；
- 第一对为空 `AB` 时不会启用 `AA` 路线，普通 `AU` 查询又没有完整单字候选，所以自然保持无候选；
- 第三对为合法 `AU` 时启用标准 `AAAU`；
- 第三对为空 `AB` 时启用 `AAA+B`；
- 第三对为空 `AA` 时不会启用 `AAA+B`，而 `AAAA` 仍可正常查询四字词。

现有 Mira 用例已经覆盖部分关键边界：

- 空 `AA` 前缀 `cw` 进入声声二字词；
- 空 `AB` 前缀 `be` 及其 `AUB` 后缀 `bea` 保持无候选，不会误入声声二字词；
- `cwyx` 的后两码也是空 `AA`，只走 `AAAA`，得到四字词而不混入三字词；
- `cwyi` 的后两码为合法音节，走 `AAAU`；
- `glyu`、`ykyu` 使用第三音节空 `AB` 回收为 `AAA+B`。

由此得到本次讨论的主要结论：**当前两套 21×26 神韵方案原则上无需修改运行行为。** 第一对空 `AB` 的保留目前是由“查不到候选且没有其他路由”自然形成的，虽然实现上没有把它命名成独立路由，但不存在已知的错误候选泄漏。

## 暂不实施的事项

以下设想保留为探索方向，不在本次讨论后直接实现：

- 不给空 `AB` 或 `AUB` 填普通词；
- 不创建“小 54”固定候选表；
- 不新增特殊功能翻译器；
- 不为了显式表达保留域而改动现行候选路由；
- 不把运行时空桶直接当成永久功能键位合同。

## 铺路实施状态

本轮已经完成：

1. 静态回归锁定结构容量 `138 AA + 9 AB = 147`、当前运行时容量 `134 AA + 9 AB = 143`、9 个空 `AB` 的准确名单以及 45 个 `AUB`、225 个 `AUBB` 的派生容量。
2. 两套 21×26 方案各用 `be`、`bea` 增加候选级代表回归，验证第一对空 `AB` 及其 `AUB` 后缀当前保持无候选。
3. 两份 README 的简体、英文、繁体段落和 README 生成脚本同步写明 `134 AA + 9 AB = 143`，文档测试锁定该表述。

仍留给未来特殊功能设计处理：

1. 若有维护需要，可在路由代码或测试命名中显式区分 `vacant_AA` 与 `vacant_AB`，但不应借此改变现行行为。
2. 映射、音节集合或系统词典变化时重新审计 9 个空 `AB`；若名单变化，应明确判断是预期迁移还是回归。
3. 真正启用特殊功能前，先决定采用结构空桶还是运行时空桶。长期稳定的功能入口应优先使用冻结的结构空桶，并在生成或测试阶段检查碰撞。
4. 为特殊功能定义退出、顶屏、补码、用户词典隔离和候选优先级规则之后，再决定是否开放 `AB`、`AUB` 或 `AUBB` 的某一层。

## 最终结论

飞码四码顶在 21×26 键域中的判长规则可以概括为：空桶必须同时看位置和下一键类别。后半空 `AB` 才能推断三字词，后半空 `AA` 仍走四字词；前半空 `AA` 才能推断声声二字词，前半空 `AB` 则属于独立保留域。

现行冰雪神韵·形和冰雪神韵·调已经实现了这一行为边界，因此当前工作重点不是改方案，而是补充容量审计、回归测试和未来特殊功能的稳定码位合同。
